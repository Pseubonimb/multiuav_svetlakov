# MultiUAV + Cosys-AirSim + Unreal Engine 5.8 на Ubuntu 22.04: опыт первого запуска

Дата: 18.10.2026. Итог: группа из 5 дронов облетела квадрат 40 × 40 м в Unreal без столкновений.

## Конфигурация

| Компонент | Версия / путь |
|---|---|
| ОС | Ubuntu 22.04, Python 3.10.12, ноутбук с NVIDIA (6 ядер / 12 потоков, 15 ГБ ОЗУ) |
| Unreal Engine | 5.8.3, `~/Downloads/UnrealEngine5` |
| Плагин Cosys-AirSim | 3.5.0 (готовый Linux-плагин, собран под UE 5.8.2) |
| Проект Unreal | `Blocks_editor_project_58_350.zip` → `~/Downloads/Blocks 5.8/` |
| MultiUAV | форк `Pseubonimb/multiuav_svetlakov` → `~/Documents/multiuav_svetlakov` |

| Настройки AirSim | `~/Documents/AirSim/settings.json` (создаёт `multiuav settings`) |

## Архитектура (что я понял)

- **Unreal Engine** — мир, рендер, столкновения с геометрией карты. Полётом дрона он не управляет.
- **Плагин Cosys-AirSim** (внутри процесса Unreal) — собственная физика мультикоптера (тяга роторов, сопротивление), автопилот SimpleFlight, сенсоры, RPC-сервер на порту 41451.
- **MultiUAV** — отдельная программа на Python, не плагин. Читает сценарий YAML, спрашивает алгоритмы о командах RC (1000–2000), переводит их в `moveByRollPitchYawrateZAsync` и шлёт по RPC. Своей физики для Unreal нет; есть упрощённый симулятор `kinematic` для отладки без Unreal.
- **settings.json** — единственная связь: в нём записаны дроны `Drone0…DroneN`. Плагин читает его только при нажатии Play.

Исходное заблуждение: «MultiUAV использует физику UE5, а модели Cosys подключаются как плагин». На деле физику полёта считает AirSim, а MultiUAV — внешний клиент.

### Как MultiUAV общается с AirSim: RPC

- **RPC (Remote Procedure Call)** — способ вызвать функцию в другом процессе как обычную. Это подход, а не конкретный протокол.
- В AirSim используется **msgpack-rpc**: Python-клиент `cosysairsim` упаковывает имя функции и аргументы в MessagePack и отправляет по TCP на порт 41451. RPC-сервер плагина (`rpclib`) вызывает настоящую C++-функцию и возвращает ответ. Строка `Client Ver:4 ... Server Ver:4` при подключении — проверка совместимости API.
- В отличие от MAVLink (фиксированный набор сообщений для дронов, поток по UDP или радио), здесь набор «команд» — это просто функции API AirSim. MAVLink и `RC_CHANNELS_OVERRIDE` в этой связке не используются.
- «RC Override» в MultiUAV — только **внутренний формат** команд алгоритмов: 4 канала 1000–2000. Цепочка:
  1. алгоритм возвращает `RcOverride`;
  2. `rc_to_setpoint` переводит его в углы ±30°, скорость рысканья ±90°/с, вертикальную скорость ±3 м/с (газ = скорость подъёма, как в AltHold);
  3. `cosys.py` вызывает по RPC `moveByRollPitchYawrateZAsync`;
  4. SimpleFlight своими PID-регуляторами управляет моторами.
- Формат RC выбран, видимо, ради переноса на реальный ArduPilot. Там нужна отдельная проверка: другие регуляторы, есть failsafe. Настоящий MAVLink появился бы только с ArduPilot SITL вместо SimpleFlight, а MultiUAV этого пока не умеет.

## Точки входа и выходные данные

Одна точка входа: `python -m multiuav <команда>`.

| Команда | Что делает |
|---|---|
| `run <сценарий>` | Один прогон; `--backend kinematic\|cosys`, `--drones`, `--algorithm`, `--leader`, `--out папка`, `--plot файл.png` |
| `compare <сценарий>` | Серия прогонов только в `kinematic`: по умолчанию `single_file,leader_path` × `3,5,7,10` дронов |
| `settings <сценарий> --write` | Пишет `~/Documents/AirSim/settings.json` |
| `gamepad` | Показывает оси геймпада |

Где смотреть результаты:
- терминал — сводка JSON в конце прогона;
- `--out runs/X/` — `track.csv` (t, drone, north, east, altitude, yaw, collided; 20 строк в секунду на дрон) и `summary.json`;
- `--plot` — вид сверху с траекториями;
- Unreal — окно игры (клавиши `F1`, `F`, `B`, `M`), Output Log, `<проект>/Saved/Logs/`;
- лог сборки Unreal — `~/.config/Epic/UnrealBuildTool/Log.txt`.

### 4. Проверка без Unreal

### 5. Окно «Convert Project» при открытии
- В поле Project Location открывался `~/Downloads/Blocks 5.8/Blocks.uproject`.
- Причина: проект и готовые бинарники плагина под 5.8.2, а движок 5.8.3 → Unreal пересобирает C++-модули.
- Системе это не вредит, касается только одного проекта.

### 6. «UnrealEditor is not responding» без конца
- Причина: GNOME проверяет отклик окна, а редактор занят сборкой. На сборку кнопка Wait не влияет.
- Решение: `gsettings set org.gnome.mutter check-alive-timeout 60000` (откат: `gsettings reset org.gnome.mutter check-alive-timeout`).

### 7. Сборка висела на 1% больше 23 минут — главная проблема
- Симптомы: три `clang++` на 100% CPU, но по 30 МБ памяти и всего 24 КБ прочитано; в процессе загружена `libUbaDetours.so`. Тот же `clang++` вручную без UBA отрабатывал за 0,04 с.
- Причина: **UBA (Unreal Build Accelerator)**, по умолчанию включённый в UE 5.8, зацикливал компилятор.
- Варианты: ждать дальше; бросить и взять готовый `Blocks.sh`; отключить UBA.
- **Выбор: отключить UBA.**
  1. `pkill -f UnrealBuildTool; pkill clang++; pkill UnrealEditor`
  2. `~/.config/Unreal Engine/UnrealBuildTool/BuildConfiguration.xml`:
     ```xml
     <?xml version="1.0" encoding="utf-8" ?>
     <Configuration xmlns="https://www.unrealengine.com/BuildConfiguration">
       <BuildConfiguration>
         <bAllowUBAExecutor>false</bAllowUBAExecutor>
       </BuildConfiguration>
     </Configuration>
     ```
     (в 5.8 старое `bAllowUBALocalExecutor` устарело; путь с пробелом открывать в кавычках: `nano ~/".config/Unreal Engine/UnrealBuildTool/BuildConfiguration.xml"`)
  3. Сборка из терминала, чтобы видеть прогресс:
     ```bash
     ~/Downloads/UnrealEngine5/Engine/Build/BatchFiles/Linux/Build.sh BlocksEditor Linux Development -Project="$HOME/Downloads/Blocks 5.8/Blocks.uproject"
     ```
- Результат: 80 действий с меткой `[NoUba]`, `Result: Succeeded` за 190 с. Нормальный признак работы — у `clang++` сотни МБ памяти.
- Безвредно: жёлтые предупреждения про `stdc++`/`supc++` и `CompressImageArray is deprecated`.

### 8. Окно «Compile Failed … Terminated» в редакторе
- Причина: это старая сборка, убитая `pkill` на шаге 7. Нажал Cancel, редактор закрылся — так и нужно, сборка в терминале продолжилась независимо.

### 9. Запуск редактора и первый полёт
- **Alias `ue5`** — короткая команда для запуска редактора на дискретной видеокарте. Ноутбук гибридный (NVIDIA RTX 4050 + встроенная AMD Radeon), и без переменных PRIME приложение может рисоваться на слабой встроенной карте. Строка в конце `~/.bashrc` (у меня — строка 122):
  ```bash
  alias ue5='__NV_PRIME_RENDER_OFFLOAD=1 __GLX_VENDOR_LIBRARY_NAME=nvidia ~/Downloads/UnrealEngine5/Engine/Binaries/Linux/UnrealEditor'
  ```
  - `__NV_PRIME_RENDER_OFFLOAD=1` — отдать отрисовку дискретной NVIDIA (PRIME render offload);
  - `__GLX_VENDOR_LIBRARY_NAME=nvidia` — использовать графическую библиотеку NVIDIA;
  - всё, что написано после `ue5`, передаётся редактору, например путь к `.uproject` или `-game`.
  
  Как добавить: дописать строку в `~/.bashrc` (например, `nano ~/.bashrc`, вставить в конец, сохранить `Ctrl+O`, выйти `Ctrl+X`), затем `source ~/.bashrc` или открыть новый терминал. Проверка: `type ue5`. Проверить, какая карта рисует: `nvidia-smi` во время работы редактора должен показывать `UnrealEditor`.
- Запуск через свой alias (дискретная NVIDIA через PRIME):
  ```bash
  ue5 "$HOME/Downloads/Blocks 5.8/Blocks.uproject"
  ```
  Первый запуск — долгая компиляция шейдеров (разово, дальше из кэша `~/.config/Epic/UnrealEngine/Common/DerivedDataCache`). Открылась карта `FlyingExampleMap`.
- Порядок: **settings → Play → run**:
  ```bash
  python -m multiuav settings scenarios/blocks_demo.yaml --write
  # в редакторе: Play
  python -m multiuav run scenarios/blocks_demo.yaml --backend cosys --out runs/blocks1 --plot runs/blocks1.png
  ```
- Результат: `Connected!`, версии клиента и сервера совпали; 5 дронов, квадрат 40 × 40 м на 30 м (высота 29–31 м), столкновений 0.
- `finished: 0` — не ошибка: в `blocks_demo.yaml` нет зоны `finish`, прогон шёл до `duration_s: 120`.
- Волны на углах траекторий — реальная инерция в физике AirSim, которой нет в `kinematic`.

### 11. Редактор падает в случайные моменты (20.10.2026)
- Симптомы: в логе `VK_ERROR_DEVICE_LOST`, `TerminateOnGPUCrash`; в «GPU breadcrumbs» активны `RayTracingScene`, `Nanite::ShadeBinning`, `LumenSceneLighting`. Падения в 17:42 и 17:56, в 17:45 — `Segmentation fault`. Падало и на `FlyingExampleMap`, то есть не из-за Cesium.
- Причина: сбой видеокарты (RTX 4050 Laptop, 6 ГБ, драйвер 595.99.02), а не нехватка CPU или ОЗУ (свободно около 10 ГБ; второй Claude ресурсов почти не ест). В `Blocks 5.8/Config/DefaultEngine.ini` была включена **аппаратная трассировка лучей** под Vulkan (`r.RayTracing`, `r.Lumen.HardwareRayTracing`, `r.Vulkan.RayTracing` и др.) — самый тяжёлый и нестабильный режим для ноутбучной карты на Linux.
- Решение: аппаратная трассировка выключена (5 параметров `=False`), Lumen работает в программном режиме — картинка почти та же. Копия: `DefaultEngine.ini.bak-before-no-hwrt`. Файл с окончаниями строк CRLF: `sed` без учёта `\r` ничего не меняет. После этого первый запуск снова компилирует шейдеры.
- Если падения останутся: в редакторе Settings → Engine Scalability → High или Medium; следующий шаг — `r.Shadow.Virtual.Enable=0`.
- **Уточнение (23:06):** после отключения трассировки падение повторилось, причём уже на простом выводе кадра (breadcrumbs: только `Slate` и `EndDrawingViewport`). Во всех 4 логах `VK_ERROR_DEVICE_LOST` наступает в пределах секунды после `AcquireNextImage() failed due to the outdated swapchain` — то есть когда меняется окно (размер, разворачивание, всплывающее окно, переключение фокуса). Ноутбук гибридный: рисует NVIDIA, а экран подключён к встроенной AMD Radeon (PRIME render offload, X11). Сбой — в передаче кадра между картами при пересоздании swapchain, а не в тяжести сцены. Ошибок `Xid` в журнале ядра нет; есть 64 исправленных ошибки PCIe `BadTLP` у NVIDIA за загрузку (сами по себе безвредны).
  - Обход: сразу развернуть редактор и не менять размер окна; токен вставлять в поле **Ion Access Token** у «Google Photorealistic 3D Tiles» в панели Details, а не через отдельное окно Token.
  - Радикально: переключить X на NVIDIA (`sudo prime-select nvidia` + перезагрузка, откат — `prime-select on-demand`) или сменить версию драйвера.
- Отдельно: `LogCesiumEditor: Error: Exception: Request failed: ConnectionError` — сбой связи с Cesium ion из-за слабого интернета, а не падение.

### 12. Токен Cesium и «лишние» геопривязки (21.10.2026)
- Диалог Token в редакторе при создании токена отвечал `Received response code 404`. Обход: на сайте ion.cesium.com добавить «Google Photorealistic 3D Tiles» в My Assets (Asset Depot), скопировать **Default Token** со страницы Access Tokens и вставить его в поле **Ion Access Token** у актора тайлов в Details. После этого тайлы пошли.
- Тайлы показывали Денвер: появилась вторая геопривязка с местом по умолчанию (39.736401). Причина в коде Cesium (`ACesiumGeoreference::GetDefaultGeoreference`): «главной» считается геопривязка с тегом актора **`DEFAULT_GEOREFERENCE`**, а созданная скриптом его не имела. Без тега Cesium создаёт новую (`CesiumGeoreference1`, `2`, …) при каждом удалении.
- Решение: у своей `CesiumGeoreference` в Details → Actor → **Tags** добавить `DEFAULT_GEOREFERENCE`, затем удалить лишнюю. В скрипте создания карты нужно ставить тег сразу: `georef.tags = [unreal.Name("DEFAULT_GEOREFERENCE")]`.

### 13. Итог по Cesium (21.10.2026)
- Заработало: рой летает над реальным кампусом Google в UE5. Перед полётом пришлось перенести старт на открытое место (**Place Georeference Origin Here**): исходная точка была под крышей Bay View (`Collision ... with Cesium3DTileset_0`).
- Видеопамять: Google-тайлы заняли около 5,6 из 6 ГБ (`Failed to allocate Device Memory`). Помогают: Maximum Screen Space Error 16 → 32 у тайлсета, `scalability 1` в консоли редактора (Medium), закрытый браузер.
- **Ограничение:** вблизи тайлы низкополигональные. Это фотограмметрия по аэросъёмке: дома и деревья — «оплывшие» коробки с текстурой, коллизии тоже грубые. Хорошо смотрится с высоты 50–100 м и выше; для полётов на малой высоте (между домами, под кронами) проигрывает нормальным картам UE5 из готовых 3D-моделей.
- Варианты для малых высот: снизить Maximum Screen Space Error (8–16) рядом с местом полёта, если хватит видеопамяти; собрать участок вручную (Landscape + модели) и оставить Cesium дальним фоном; Cesium OSM Buildings — чистая, но простая геометрия без текстур; готовые карты с Fab — на Linux только неофициальными путями.

### 14. Пульт, группа, камеры, обход без связи, скрипт запуска (28.10.2026, делал Claude)

### 18. Пульт с запаздыванием и падение Unreal из-за камер (28.10.2026)

### 19. Ведомые не взлетали после посадки (28.10.2026)
- Журнал `runs/demo_20261028_173357`: ведущий сел и снова поднялся на 7–12 м, а ведомые 2–4 остались на земле на всё оставшееся время, газ 1494–1505 («держать высоту»).
- Причина 1 — не трение, а зрение. Лидар — веер ±15°, точки дальше 2 м ниже лидара отбрасываются (`LIDAR_BELOW`). У земли нижние лучи бьют в неё в 2–4 м вокруг, это принимается за стены, все соседи «заслонены» — ведомый никого не видит и держит высоту последней увиденной цели (землю). Идея пользователя: «не давать садиться ниже hf». Геометрическая hf = 20 м × sin 15° ≈ 5 м и растёт с наклоном дрона, но у нас фильтр работает в мировых осях, поэтому фактический порог — 2 м + 0,3 м (лидар выше центра) + запас ≈ 3 м.
- Причина 2 (и у ведущего): в AltHold газ копится в целевую высоту. Стоя на земле с газом вниз, цель «уходит под землю», и потом нужно время, чтобы её вернуть. Теперь цель не ниже 1 м под точкой старта (`GROUND_Z`).
- Сделано:
  - `min_altitude` у ведомых `visual_follow`/`flock` (по умолчанию 3 м): садится ведущий — ведомые зависают на 3 м и продолжают видеть.
  - Клавиша **L** (в русской раскладке — «Д») в терминале, где идёт `run`: ведомые останавливаются и мягко садятся (цель на 1 м ниже текущей высоты, ~1 м/с); ещё раз L — взлетают на свою высоту. Строка `MultiUAV: FOLLOWERS: LANDING/TAKEOFF` в окне Unreal. Модуль `multiuav/keyboard.py` (cbreak, Ctrl+C работает).
  - В kinematic мягкое касание земли (медленнее 1,5 м/с вниз) — посадка, а не авария.
- Проверено в kinematic: ведущий сел на 0,3 м, ведомые держали 3 м; L — сели без столкновений; L — поднялись на 3 м. В Unreal и с пультом не проверено.
- Столкновения в файле: `track.csv`, столбец `collided`, у всех дронов, включая ведущего; `summary.json` — время первого столкновения каждого. Касания земли тоже считаются столкновениями, и с чем столкнулся — не пишется.

  - дрон появляется на −0,7 м и «прилипает» к земле (ground lock в `FastPhysicsEngine`): `takeoffAsync` первые секунды не взлетает;
  - Unreal не всегда закрывается по `kill` за 6 с — тогда новый не может занять порт 41451, а скрипт подключается к старому; закрывать `kill`, затем `kill -9`.

### 23. Сопротивление винтов — дрон больше не «на льду» (30.10.2026)
- Причина «льда»: в `FastPhysicsEngine::getDragWrench` есть только сопротивление корпуса ~v², а линейный член отброшен («b << c»). У настоящего дрона он большой — rotor drag: лопасть, идущая навстречу потоку, тянет сильнее, и появляется сила против скорости поперёк оси винтов, пропорциональная тяге. Прошивка тут ни при чём: PX4 и ArduPilot в AirSim считаются тем же движком.
- Сделано (`airsim_patches/04-rotor-drag.patch`, накладывать после 02; копии — `*.bak-before-rotor-drag`): ключ `"RotorDrag": k` у дрона в settings.json → `MultiRotorParams::Params::rotor_drag_coefficient` → `PhysicsBody::getRotorDragCoefficient()` → в `getNextKinematicsNoCollision` добавлена сила `F = −k · T · (vₓ, v_y, 0)` в осях корпуса (T — суммарная тяга винтов, скорость — относительно ветра). Без ключа `k = 0`, всё как в исходном AirSim.
- В MultiUAV: `rotor_drag: 0.035` в сценарии → `"RotorDrag"`. В `kinematic` похожее сопротивление было всегда (`drag = 0.35` 1/с ≈ k 0,036 на висении) — поэтому там «льда» и не было. `rc_single.yaml`: `fast2.5` + `rotor_drag: 0.035`.
- Замеры на Fast2.5 (Blocks, `acrotest.py`, тесты `glide,top,turn,brake`):

  | k, с/м | Скольжение с 15 м/с в горизонте: до 7,5 / до 2 м/с, путь | Скорость на 60° за 10 с | Разгон 0→20 м/с на 45° | Поворот 90° на 15 м/с |
  |---|---|---|---|---|
  | 0 | 11 с / >15 с, **145 м** | высоту не удержал | 2,4 с | 1,7 с, снос 9 м |
  | 0,02 | 2,8 / 8,8 с, 55 м | 28 м/с | 4,0 с | 1,6 с, 9 м |
  | 0,035 | 1,6 / 5,1 с, **31 м** | 23 м/с | не за 10 с | 1,6 с, 7 м |
  | 0,05 | 0,8 / 3,4 с, 18 м | 20 м/с | не за 10 с | не успел за 8 с |

- Плата за сцепление — потолок скорости: на k = 0,035 на 45° дрон не набирает 20 м/с. Нужна скорость — уменьшать k (0,02) или наклоняться сильнее. Отдельно не разбирал, почему потолок падает сильнее, чем по моей оценке: вероятно, сказывается вместе с сопротивлением корпуса.
- С пульта не проверено. На карте Виталия не действует, пока он не соберёт игру с патчами 01–04.
- Сводный отчёт по разделам 21–23 — `docs/drone_physics_report.md`; скрипты замеров перенесены в `scripts/physics_tests/` (`run_model.sh`, `acrotest.py`, `althold.py`).
- Урок: Python `open().read()/write()` молча переводит окончания строк CRLF → LF (так было с `PhysicsBody.hpp`, `FastPhysicsEngine.hpp`, `MultiRotorParams.hpp`) — патч раздулся до 2666 строк. Исправлено `sed -i 's/$/\r/'`; проверять `grep -c $'\r'` до и после.

### 25. Журнал стиков пульта через evdev (30.10.2026)
- Зачем: исследовать тремор оператора. Логгер — отдельный процесс от симулятора, читает пульт напрямую из ядра (`/dev/input/eventN`, модуль `evdev`, extra `sticks`). Симулятор (pygame) читает тот же пульт параллельно, захват (`grab`) не делается.
- Пульт: **EdgeTX Radiomaster Pocket Joystick**, `/dev/input/event22` (номер меняется, ищется по имени), читается без sudo. 8 осей, у всех `Min 0`, `Max 2047`, по умолчанию **`Fuzz 7`, `Flat 127`** — ядро срезало изменения меньше 7 единиц, то есть часть тремора.
- Соответствие стиков (`radio/sticks_map.json`, сделано `sticks map`): газ — `ABS_Z` (код 2, **обратная**: вверху 0, внизу 2047), рыскание — `ABS_RX` (3), тангаж — `ABS_Y` (1), крен — `ABS_X` (0). В `*_us` уже приведено к «вверх/вправо = 2000».
- Команды:
  ```bash
  python -m multiuav sticks list     # оси, Min/Max/Fuzz/Flat
  python -m multiuav sticks map      # разметить стики заново (другой пульт или модель)
  python -m multiuav sticks log --profile "Модель X: расходы 100%, expo 0" --adc-filter off --out runs/NAME
  ```
- Что делает `log`:
  - обнуляет `Fuzz` и `Flat` у всех осей (до отключения пульта; видят все программы, включая симулятор — у pygame пропадает мёртвая зона). `--keep-fuzz` — не трогать;
  - `sticks.csv`: `t_ms` — `time.time_ns() // 1_000_000` при чтении (общие часы, без отсчёта от нуля), `evdev_us` — метка ядра в мкс на тех же часах, сырые значения 4 стиков и они же в 1000–2000. Строка на каждый `SYN_REPORT`, где что-то сдвинулось;
  - каждая строка `flush` сразу (переживает падение скрипта), `fsync` раз в секунду (переживает отключение питания; `--fsync` — после каждой строки);
  - `passport.json`: устройство, оси (`Min`/`Max`, `Fuzz`/`Flat` до и после), соответствие, профиль EdgeTX и фильтр АЦП (по USB не читаются — пишутся из `--profile` и `--adc-filter`), число строк, потери событий `SYN_DROPPED`, причина остановки. Записан в начале и обновлён в конце;
  - при `SYN_DROPPED` (переполнился буфер ядра) события до следующего `SYN_REPORT` отбрасываются, положение перечитывается у ядра.
- Проверка (`runs/sticks_test`): 5730 строк за 59 с, шаг 1–2 мс (пульт шлёт ~500 пачек/с), `SYN_DROPPED` 0. Без Fuzz в покое видно дрожание рыскания 1013–1028 из 2047.
- Пульт отдаёт каналы уже после микшера EdgeTX: экспоненты, расходы и кривые попадают в данные. Нужен один зафиксированный профиль модели на все эксперименты; фильтр АЦП (System → Hardware → ADC filter) для анализа тремора выключить.
- Каналы, ушедшие дрону, остаются в журнале прогона; склейка — по `t_ms`.
